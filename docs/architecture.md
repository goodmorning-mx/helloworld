# Architecture

The product contains three local services:

- `frontend`: the React/Vite trading workspace.
- `backend`: FastAPI API, shared Binance market gateway, Tracker workers, account services, and scanner.
- `postgres`: authenticated user data, Paper operations, execution intents, and worker configuration/runtime.

Runtime configuration is supplied through environment variables documented in `.env.example`.

## Realtime Tracker engine

The first realtime execution path is Paper. One `BinanceMarketGateway` owns the public Futures stream per symbol in a backend process. It normalizes and caches candles and fans events to chart clients and strategy workers. A cold worker seeds that same gateway from Binance REST, then uses only completed candles from the selected interval. The Tracker rules and close-at-candle semantics are shared with the existing strategy module.

Market fanout calls a synchronous enqueue-only callback for each worker. Each worker has a bounded 64-candle queue and its own asyncio task; database calls are moved off the event loop. On queue pressure, the worker reports `DEGRADED` and catches up from the gateway's bounded 1,500-candle snapshot. It exposes queue depth, processed/received/duplicate counts, overflows, last processed candle, decision latency, status, and last error through `GET /trading/production/workers`. The frontend reloads this endpoint for the selected symbol, so the run control reflects backend state after a page refresh.

Worker configuration and runtime cursor are durable in PostgreSQL. Each symbol has a 45-second database lease renewed every 15 seconds and before candle processing; a second API instance cannot claim an unexpired lease. The worker persists its candle cursor after successful processing and resumes newer candles from the retained market snapshot. If downtime exceeds the retained candle window, it marks the worker degraded and resumes from the latest closed candle rather than claiming complete replay. Paper engine rows are tagged `source=realtime-engine`, manual Paper rows keep their separate source, and a unique per-user decision key prevents duplicate entry rows after retry. Shutdown drains each queue for up to ten seconds, releases leases, and leaves enabled configuration for startup recovery.

When a worker opens a Tracker operation from a completed candle, it publishes a structured `TRACKER_SIGNAL` event to the same backend event bus used by the engine. The Telegram sink enqueues a concise Paper/Live notification containing symbol, side, Tracker level, price, interval, UTC candle time, and configured SL/TP. The signal ID is stable per symbol, interval, candle, side, and level; the bounded sink suppresses duplicates across workers. Telegram delivery stays asynchronous and delivery errors are logged without request URLs or bot credentials. Notifications require the backend runtime variables `TELEGRAM_ENABLED=true`, `TELEGRAM_BOT_TOKEN`, and `TELEGRAM_CHAT_ID` to be set, and a Tracker worker must be running for the symbol. Repository GitHub secrets do not configure the separate Coolify runtime.

Telegram command polling is opt-in (`TELEGRAM_COMMANDS_ENABLED=false` by default), bound to the configured `TELEGRAM_CHAT_ID` and one `TELEGRAM_COMMAND_USER_ID`. It supports `/workers`, `/startpaper SYMBOL`, `/stoppaper SYMBOL`, and `/help`. It exposes no Live command. Do not configure Telegram webhook delivery at the same time as this `getUpdates` poller.

The production worker Live adapter remains behind three gates: `BINANCE_REAL_TRADING_ENABLED=false`, `PRODUCTION_WORKER_LIVE_ENABLED=false`, and `PRODUCTION_WORKER_RESUME_LIVE=false` by default. The dedicated engine Live gate remains disabled until fill reconciliation, partial fills, protection-order lifecycle, sizing parity, and exchange-side idempotency pass a separate validation. This realtime Paper work does not authorize enabling the gates or sending orders. The existing standalone real-order API has its own Binance gate.

The market cache and stream are process-local. The database lease prevents duplicate ownership across API replicas, but candle delivery is not yet a shared cross-replica event bus: a worker can recover only the gateway snapshot retained by its owning process. For multi-replica deployment with gap-free replay beyond that window, add a durable shared candle log/stream and validate it under failover before increasing replica count.

## Binance market scanner

The frontend requests the active market universe, then analyzes its symbols one at a time and updates each card as its result arrives. Tracker optimization is CPU-heavy Python work, so running several symbols at once contends for the GIL and increases each symbol's wall time. The active-universe endpoint requests only `horizon + 1` candles per symbol and loads symbols with bounded concurrency. The backend keeps a short-lived, process-local universe snapshot and a bounded cache of up to 480 closed 1m candles per scanner symbol, matching the selected-symbol Tracker's rolling 8-hour analysis window. A cold scanner cache fills that window in one Binance-sized page; later refreshes re-fetch the last cached candle and append only the missing candles. Scanner candles and analyses expire after 8 hours without a successful refresh; expiration removes associated analysis entries. The backend skips Binance requests while it already has the latest expected closed 1m candle. Scanner cards and the selected-symbol Tracker panel use the same candle window, per-symbol leverage, TP optimization, and loss limit. The selected panel asks the backend for trade details at the cached optimal TP; those details are reconstructed on demand and are not retained in the scanner summary cache. Only closed 1m candles enter Tracker analysis.

Analysis results are cached per symbol, strategy configuration, and latest closed candle time. Identical in-flight candle refreshes and analysis calculations are shared. A failed refresh keeps the last good result and reports `STALE`; a symbol without a usable result reports a recoverable `ERROR`. The frontend merges responses by symbol and keeps the previous metrics visible across refresh failures.

These scanner caches hold derived public market data in memory, are bounded, and rebuild after a backend restart. The browser keeps rolling two-day OHLC caches per symbol and interval. Live IndexedDB data uses one row per candle, so an update appends a new row or replaces only the still-open candle; startup catch-up requests begin after the latest cached candle once the last expected candle is missing, then page through any gap. An upgrade migrates the previous live per-series records. Live buffers drop candles outside the 48-hour window, and IndexedDB is swept hourly so unused rows are physically removed after they age out. The chart appends/updates only the current Heikin-Ashi point. RSI, SSL, Tracker, wick, and daily-window series retain prior output and recompute the current point, including when the rolling window advances; SVG paths and markers render only for the visible chart range. The Lab's 30-day history keeps its separate 31-day array cache so its less frequent bulk loads avoid per-candle storage overhead and the live-chart retention policy does not truncate its input. Separate backend replicas have separate scanner caches; shared cache infrastructure should be considered only if the deployment scales horizontally and measurements show the duplicated work matters.
