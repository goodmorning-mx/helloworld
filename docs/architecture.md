# Architecture

The product contains three local services:

- `frontend`: the React/Vite trading workspace.
- `backend`: FastAPI API, shared Binance market gateway, Tracker workers, account services, and scanner.
- `postgres`: authenticated user data, Paper operations, execution intents, and worker configuration/runtime.

Runtime configuration is supplied through environment variables documented in `.env.example`.

## Realtime Tracker engine

The first realtime execution path is Paper. One `BinanceMarketGateway` owns the public Futures stream per symbol in a backend process. It normalizes and caches candles and fans events to chart clients and strategy workers. A cold worker seeds that same gateway from Binance REST, then uses only completed candles from the selected interval. The Tracker rules and close-at-candle semantics are shared with the existing strategy module.

Market fanout calls a synchronous enqueue-only callback for each worker. Each worker has a bounded 64-candle queue and its own asyncio task; database and calibration work are moved off the event loop. The strategy retains at most 480 closed candles (8h at 1m). On queue pressure, the worker reports `DEGRADED` and catches up from the gateway's bounded market snapshot. It exposes queue depth, processed/received/duplicate counts, overflows, last processed candle, decision latency, status, adaptive parameters, Tracker position, and last error through `GET /trading/production/workers`. The frontend reloads this endpoint for the selected symbol, so the run control and parameter card reflect backend state after a page refresh.

Worker configuration and runtime cursor are durable in PostgreSQL. Each symbol has a 45-second database lease renewed every 15 seconds and before candle processing; a second API instance cannot claim an unexpired lease. The worker persists its candle cursor, Tracker virtual operation, and parameter snapshot after successful processing and resumes newer candles in order from the retained market snapshot. If downtime exceeds the retained candle window, it marks the worker degraded and resumes from the latest closed candle rather than claiming complete replay. Paper engine rows are tagged `source=realtime-engine`, manual Paper rows keep their separate source, and a unique per-user decision key prevents duplicate entry rows after retry. Shutdown drains each queue for up to ten seconds, releases leases, and leaves enabled configuration for startup recovery.

Tracker is the strategy authority. Its virtual position and signal sequence are independent from the Paper or Binance execution position: an execution-side SL/TP can close its own position without changing Tracker state. A Tracker close recalibrates the next parameter snapshot against the rolling 8h closed-candle window, testing Levels N from 4 through 20 and TP candidates in 0.5% increments. Historical MINROE is stored as levered ROE and converted to an underlying price stop by dividing by leverage; the executable SL is bounded from 0.05% to 20% of price. Calibration runs in a background thread, publishes a versioned `TRACKER_PARAMETERS_UPDATED` event, and the next candle waits for that snapshot before evaluating. The recalibration updates the independent Paper position's protection prices and the virtual Tracker operation's SL/TP thresholds without changing either position's entry/side or using execution exits to drive Tracker. The Binance adapter remains deployment-gated and needs exchange Algo protection replacement/reconciliation before it can consume those mid-position updates. The optimizer requires 120 closed candles; before that it reports `INSUFFICIENT_HISTORY` and uses safe defaults N=5, SL=0.2%, TP=1.0%. Risk percent, balance, and leverage come from the worker start payload and are persisted with its symbol config. Paper notional is bounded by balance × leverage, so the actual loss budget can be lower than the requested risk when the cap binds.

The Telegram command interface controls one leased Tracker session per user. `/scan` returns the shared scanner ranking; `/start SYMBOL` switches to that symbol and starts the Tracker in `signals_only`; `/paper` selects Paper execution for future Tracker signals; `/production` requests Live execution and remains rejected until Live reconciliation and protection validation are complete; `/stop` stops the active session; `/status` and `/help` report state and usage. Existing Paper operations retain the adapter that opened them when the mode changes, while future Tracker signals use the selected adapter. Symbol switching is rejected while an execution operation is still open so it cannot be orphaned without its manager. The worker emits Tracker signals independently of execution mode.

Telegram command polling requires `TELEGRAM_COMMANDS_ENABLED=true`, a configured bot token/chat, the internal owner ID, and an allowlisted sender ID. The bounded asynchronous sink sends deduplicated Tracker signals and compact operation close summaries when `TELEGRAM_SIGNAL_NOTIFICATIONS_ENABLED=true`; parameter recalibration and worker lifecycle events are suppressed. Both settings default on in the sample/local configuration, but empty credentials and allowlist values keep the integration inactive. Telegram long polling must run in one backend replica only; for horizontal scaling, replace it with a webhook or database leader lease.

The configuration table persists the selected worker mode, while `production_worker_sessions` holds a 45-second per-user lease renewed every 15 seconds. This lease enforces one active session across backend replicas; the per-symbol runtime lease still protects each worker's cursor and state. A switch is serialized per user in-process, releases the previous session before taking the new symbol, and rejects a switch/stop while a Paper operation is open rather than leaving an unmonitored operation.

The production worker Live adapter remains behind four gates: `BINANCE_REAL_TRADING_ENABLED=false`, `PRODUCTION_WORKER_LIVE_ENABLED=false`, `PRODUCTION_WORKER_LIVE_VALIDATED=false`, and `PRODUCTION_WORKER_RESUME_LIVE=false` by default. `/production` waits for a healthy User Data Stream, positive available balance, exchange margin/leverage confirmation, and valid symbol filters; then it arms Live for future Tracker signals. Live order placement remains impossible until all gates are enabled. The independent standalone real-order API has its own Binance gate.

The market cache and stream are process-local. The database lease prevents duplicate ownership across API replicas, but candle delivery is not yet a shared cross-replica event bus: a worker can recover only the gateway snapshot retained by its owning process. For multi-replica deployment with gap-free replay beyond that window, add a durable shared candle log/stream and validate it under failover before increasing replica count.

## Binance market scanner

The frontend requests the active market universe, then analyzes its symbols one at a time and updates each card as its result arrives. Tracker optimization is CPU-heavy Python work, so running several symbols at once contends for the GIL and increases each symbol's wall time. The active-universe endpoint requests only `horizon + 1` candles per symbol and loads symbols with bounded concurrency. The backend keeps a short-lived, process-local universe snapshot and a bounded cache of up to 480 closed 1m candles per scanner symbol, matching the selected-symbol Tracker's rolling 8-hour analysis window. A cold scanner cache fills that window in one Binance-sized page; later refreshes re-fetch the last cached candle and append only the missing candles. Scanner candles and analyses expire after 8 hours without a successful refresh; expiration removes associated analysis entries. The backend skips Binance requests while it already has the latest expected closed 1m candle. Scanner cards and the selected-symbol Tracker panel use the same candle window, per-symbol leverage, TP optimization, and loss limit. The selected panel asks the backend for trade details at the cached optimal TP; those details are reconstructed on demand and are not retained in the scanner summary cache. Only closed 1m candles enter Tracker analysis.

Analysis results are cached per symbol, strategy configuration, and latest closed candle time. Identical in-flight candle refreshes and analysis calculations are shared. A failed refresh keeps the last good result and reports `STALE`; a symbol without a usable result reports a recoverable `ERROR`. The frontend merges responses by symbol and keeps the previous metrics visible across refresh failures.

These scanner caches hold derived public market data in memory, are bounded, and rebuild after a backend restart. The browser keeps rolling two-day OHLC caches per symbol and interval. Live IndexedDB data uses one row per candle, so an update appends a new row or replaces only the still-open candle; startup catch-up requests begin after the latest cached candle once the last expected candle is missing, then page through any gap. An upgrade migrates the previous live per-series records. Live buffers drop candles outside the 48-hour window, and IndexedDB is swept hourly so unused rows are physically removed after they age out. The chart appends/updates only the current Heikin-Ashi point. RSI, SSL, Tracker, wick, and daily-window series retain prior output and recompute the current point, including when the rolling window advances; SVG paths and markers render only for the visible chart range. The Lab's 30-day history keeps its separate 31-day array cache so its less frequent bulk loads avoid per-candle storage overhead and the live-chart retention policy does not truncate its input. Separate backend replicas have separate scanner caches; shared cache infrastructure should be considered only if the deployment scales horizontally and measurements show the duplicated work matters.
